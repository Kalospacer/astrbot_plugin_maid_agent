---

传统角色扮演 Agent 会把大量 Function Calling 系统提示词注入主模型，导致模型说话像刻板的 AI 助手、丢失沉浸感。本插件把「聊天」和「做事」拆成两个角色：

- **大小姐（主模型）**：上下文只保留纯净的自然语言对话，负责陪用户聊天、理解意图。需要做事时，通过 `maid_agent` 向管家下达指令。
- **管家（子代理 SubAgent）**：接管全部工具调用能力（Shell、Python、文件、浏览器等），在后台执行任务，最终汇报交给大小姐转述。管家的执行记录独立存放，不写进大小姐的对话历史。开关打开后，它干活途中的正文也能以 `管家名: ...` 直接说给用户听。

派活不阻塞：管家干活的同时，用户和大小姐照常聊天。

> [!WARNING]
> **开发阶段提醒**
>
> - 本项目的实现不代表该概念的最终形态，仍在积极演进中。
> - AstrBot 的 `subagent` 模块仍处于实验性阶段，本插件需 Hook 并隐藏模型可用工具；此设计可能与其他依赖「提示词注入」或「发送事件钩子」的插件冲突，同用时效果可能不达预期。
> - 遇到问题欢迎提交 issue；有创意或愿意修 bug 欢迎提交 PR。

## 运行前提

- AstrBot `>= 4.27.3`，需要主代理运行钩子与停止回调；同时支持新旧两种执行配置布局。
- 一个 subagent 都没配置也没关系：插件启动时会自动创建一个默认管家（名称取 `default_agent_name`，默认 `butler`，可以使用全部工具），已有任何 subagent 配置时绝不会覆盖。
- 想用自己配置的管家，参考文末「SubAgent 配置示例」。

---

## 快速开始

1. 启用本插件（零配置可用，默认管家会自动创建）。
2. 正常聊天。大小姐需要做事时会自动调用 `maid_agent`，管家执行并回报。
3. 想换管家时，在 `allowed_agent_names` 中加入已配置名称，并将 `default_agent_name` 设为该名称；模型无需选择名称。

## 工具 API

以下工具由插件注册给大模型，通过 function calling 调用，**用户通常无需手动触发**。每个工具只会作用于当前聊天来源创建的任务，不能跨会话操作。

### maid_agent —— 派发或恢复已结束的任务

模型不需要提供子代理名称或 session ID，统一使用插件的 `default_agent_name`。

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `prompt` | string | 单任务要求；与 `tasks` 二选一。 |
| `task_id` | string | 可选，在原上下文里恢复一项已结束的任务。 |
| `force_new` | boolean | 可选，明确创建独立分支，包括与正在执行的任务并行。不能与 `task_id` 混用。 |
| `tasks` | array | 2～5 项独立任务，每项是 `{prompt}`，自我唤醒时可附带评估表单；不能与单任务参数混用，批量本身不需要 `force_new`。 |
| `rule_assessments` / `direction` / `intent_evidence` / `scope` | | 评估表单，只在自我唤醒时填写，见下文「自我唤醒时的派发」。 |

工具立即返回任务描述、程序生成的 `task_id` 与阶段。单一/已选默认工作记录在空闲时自动沿用；新任务有新编号，但不必换一本工作笔记。同时干活的管家达到 `max_workers` 时，新任务排队，有空位后按先后启动。

已有任务正在执行时，普通派发返回错误，不自动改成追加；追加要求使用 `maid_send_message`，并行新建使用 `force_new` 或批量入口。

### maid_send_message —— 给未结束的任务追加输入

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `task_id` | string | 有多个未结束的任务时必须填写；只有一个时可省略。 |
| `message` | string | 必填，追加的要求。 |
| 评估表单字段 | | 只在自我唤醒时填写。 |

未结束的任务（正在干活、空闲或等人处理）都能接收。管家正在跑就插进这一轮，空闲就开新的一轮。目标已经结束则报错，并提示使用 `maid_agent`，不会自动转换操作。`accepted` 表示已可靠接收，不等于模型已经读取；这一轮结束仍未读到的输入会再送一次。

### maid_list_agents —— 查看任务列表

返回任务描述、`task_id`、阶段、最近一次上报的摘要、未答的问题，以及默认上下文关联。

### maid_task_output —— 读取进度或结果

按任务 ID 读一眼，**从不阻塞**。管家正在跑就返回当前进度（正在用哪个工具、最近一段正文、已跑多少秒），同时返回每次执行的上报。读过结果不影响之后的唤醒转述。

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `task_id` | string | 必填 | 任务 ID。 |

### maid_task_stop —— 停止任务

按任务 ID 停止任务：立即结束任务并取消管家正在跑的这一轮，不唤醒大小姐。停掉的任务可以用 `maid_agent(task_id)` 恢复。有人发消息时和她自我唤醒时都能停。

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `task_id` | string | 必填 | 要停止的任务 ID。 |

### 管家专用工具

以下两个工具只给管家用，大小姐看不到；不管 SubAgent 的工具怎么配置，管家都会拿到它们。

- `maid_report(state, summary, human_action?)`：上报任务状态。`ready` 表示完成（结束任务），`dropped` 表示不需要做或不是这项任务的事（结束任务），`blocked` 表示没人帮忙就做不下去，`failed` 表示失败，`progress` 是进度。`human_action` 是想问人的一个具体问题，可以和 `progress` 一起给；省略表示保留之前的问题，空字符串表示清除。
- `maid_read(resource, offset?, limit?)`：分页读取本任务的资源：`conversation` 是大小姐与用户的对话（读取时的最新内容），`input/<id>` 是被截断的请求原文，`trigger/<id>` 是被截断的触发消息原文。

## 用户命令

在聊天里直接输入，管理管家任务。

| 命令 | 说明 |
| --- | --- |
| `/maid status` | 查看当前会话运行中的管家任务：管家名、已跑秒数、正在用的工具、最近一段正文。 |
| `/maid stop` | 停止当前会话里正在干活的全部任务，返回停下的数量。 |

## 核心机制

**非阻塞派发**

派发只是把任务塞进管家的队列，工具立刻返回句柄。主模型的这一轮随即结束，AstrBot 对该会话的 agent run 也随之释放，用户接下来说的话会正常开启新的一轮，而不是被当成 follow-up 吞进工具结果里。

管家不再借用主流程的真实聊天消息——那个消息归 AstrBot 的 pipeline 所有，主流程一结束它携带的临时文件就被清理。派发时插件会抽一份快照交给管家：图片复制进会话附件区，发送者、群、平台身份与能力位一并带走。管家发消息按 UMO 走平台适配器，因此它能真正开口。

代价是短任务也变成两轮：大小姐先回一句"在做了"，结果稍后单独送到。

**管家会自己说话**

**默认关闭**，两个开关都要自己打开。默认状态下聊天里只有大小姐的最终转述，跟传统的「管家在后台干活、大小姐转告」一致。

打开 `show_maid_speech` 后，管家干活过程中每一段正文（没有正文时用推理）会以 `管家名: ...` 的形式**即时**发到聊天，用户能看到它在想什么、做到哪一步，而不是干等一个黑箱。判据是这一步带不带工具调用：带的是过程播报、立刻发；不带的是终答，留给大小姐转述，同一份结论不会出现两遍。

不少子代理（尤其是终端型的）每一步只发工具调用、根本不输出正文，这时正文投递给不了任何东西。打开 `show_maid_tool_status` 会补上「`管家名: 🔨 调用工具: xxx`」，在工具刚开始执行时发出，是这种情况下唯一的实时进度来源。代价是长任务一步一条，几十步就是几十条消息。

控制台页面没有可发送的聊天，从控制台创建的任务只在控制台里说话。

**任务与并发**

- task 管理工作身份与每轮结果，session 管理工作上下文；新任务不一定新建 session。
- 多任务并行期间，操作目标要明确，不能借一次补充选择默认。所有任务结束后，多份记录存在歧义时要求选择一次；此后普通派发自动使用该默认上下文。新批量清除默认选择。
- `force_new` 和批量创建独立分支，只继承当前主对话，不复制其他分支的内部调查过程。分支之间通过回传主对话的报告共享结论。
- 管家的工具循环不设步数和时长上限，也没有看门狗。
- 所有聊天来源合计最多 `max_workers`（默认 3）个管家同时干活；满了就排队，按先后启动，不拒绝。有人发来的新输入（追加要求、恢复任务）可以额外多用 1 个位置，并排在新任务前面。控制台会话不计入。
- 并发的多个管家会同时往同一个聊天里说话，靠 `管家名:` 前缀区分。

**任务阶段与通知**

任务处在这几种阶段之一：`working`（干活中，`working/queued` 表示排队）、`idle`（这一轮结束了，等新输入）、`person/*`（等人：`answer` 回答问题、`blocked`、`failed`、`delivery` 输入送不到）、`ended`（结束）。

管家用 `maid_report` 上报，上报一到就按状态决定是否唤醒大小姐：带问题的上报唤醒她转达问题；`ready`、`blocked`、`failed`、`dropped` 唤醒她转述结果；不带问题的 `progress` 不唤醒；停止不唤醒。管家这一轮结束却没有上报、也没把任务交还给人时，记为 `waiting`：有最后的话就唤醒转述；什么都没说又从没上报过时，唤醒并告知管家没有上报状态。每次唤醒只投递一次，并排在该会话的 session lock 后面，不会插进用户正在进行的一轮里抢写对话历史。

**管家的输入**

派发给管家的第一条消息只有任务说明（超过 1500 字截断）和触发消息（超过 600 字截断），截断处注明可用 `maid_read` 读全文。需要主对话背景时，管家用 `maid_read` 读取读取时的最新对话。追加的输入超过 1500 字同样截断。

**临时故障与重启**

管家这一轮遇到临时故障（网络、限流、上游 5xx；包括所有模型都失败时 AstrBot 给出的错误回复）时，在同一会话按 15、30、60 秒退避重试，最多 3 次；其余失败或重试用完后记为 `failed` 并唤醒大小姐。

重启后，停在稳定点（最近一次上报是 `waiting`/`ready`/`blocked`/`failed`，且之后没有新输入送达）的任务只补投没送达的输入；其余任务在同一会话带恢复说明重开，管家会先检查当前状态、不重复已完成的外部操作。排队中的任务继续排队，没完成的唤醒继续投递，已作废代次的任务不恢复。

**自我唤醒时的派发**

大小姐被定时任务或心跳插件等唤醒时（`CronMessageEvent`），这一轮不是有人发来的消息。此时调用 `maid_agent` 或 `maid_send_message` 必须填写评估表单：

- `rule_assessments`：对每条启用的规则各给一条判断（`rule_id`、`matched`、`reason`）；没有启用的规则时传空数组。
- `direction`：`implementation_requested`、`target_basis`（`specified` / `existing-standard` / `undetermined`）、`requires_design_decision`、`evidence`。
- `intent_evidence`：确立请求的原文证据；`scope`：管家可以做什么。

插件依次检查：规则覆盖是否完整（不完整报错让她重填）→ 方向是否已定（要求动手、目标有依据、不需要设计决定，否则放弃）→ 规则不为空时是否至少命中一条（否则放弃）→ 是否给了 `intent_evidence`（否则报错）。是否满足规则由她自己判断，插件只查格式。命中规则的说明会附在派发内容里。插件自己的唤醒转述那一轮同样是 `CronMessageEvent`，在那一轮派发也要填表。`inferred_dispatch` 关闭后自我唤醒时不能派发。

每次路由都会写一条判断记录（派发、恢复、停止、放弃），在控制台「判断记录」里查看。

**空闲窗口**

同一主对话共用 `session_idle_timeout_hours`，默认五小时，可配置正数小时。有任务在干活或排队时不计空闲。空闲时使用任一模型工具都会刷新活跃时间。超过窗口只刷新 session 上下文，不作废任务编号：恢复旧 `task_id` 仍定位原工作，但使用新的上下文。修改管家人格或模型保留工作记录，下一轮应用新配置。

**重置联动**

AstrBot 的 `/new`、`/reset` 停止旧执行，旧代次的任务不再启动、送达或唤醒，旧进度和报告不能再进入新对话。`/reset` 不换对话 ID，因此另有重置代次隔离。

**数据存储**：运行数据存在 `data/plugin_data/astrbot_plugin_maid_agent/maid.sqlite`（SQLite，WAL，`synchronous=FULL`，文件权限 0600，同一时间只允许一个进程使用）。任务、判断记录、主对话路由、会话事件与上下文快照都在这个库里；一次决定涉及的写入在同一个事务里提交，启动管家、送达输入和唤醒大小姐登记成副作用，提交后才执行，失败退避重试，重启后继续。图片和文件附件存 `attachments/`。数据库 schema 版本不匹配时插件拒绝启动。旧版本的 `runtime_v3/` 不读取、不迁移、不删除，升级后控制台看不到旧历史，旧任务也不能续跑。持久记忆仍独立，不随空闲窗口清除。

## 控制台

插件页提供一个聊天式控制台（AstrBot 面板 → 插件 → 代理女仆 → 控制台）：可以直接给管家派任务、看流式回复与工具调用卡片、查看每步 token 消耗；左侧可管理历史会话（搜索、重命名、删除、Fork）；右上角设置弹窗可改插件配置与主题。

侧栏底部的「判断记录」入口（设置按钮旁边）打开判断页：可以按派发、停止、忽略筛选，也可以只看最近 24 小时，每次加载 30 条；点击有任务的行会跳到对应会话。会话视图顶部还有可展开的本会话判断记录，推断派发和恢复的记录展开后能看到完整的评估表单。

> 控制台任务不会往聊天里发消息。想测试真实聊天投递（管家开口说话、发图），请在聊天里由大小姐派发。

## 配置参考

配置全部在 AstrBot 插件配置页管理。**保存严格**：类型、范围、名单或模板错误会被整单拒绝并提示具体字段，不做静默修复；**加载容错**：旧版本遗留的键会被忽略、无效值回退默认，不会导致插件无法启动，首次成功保存后配置自动规范化。

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `allowed_agent_names` | `[butler]` | 可调度的 SubAgent 白名单，不能为空。 |
| `default_agent_name` | `butler` | 模型派发统一使用的管家；没有任何 subagent 时自动创建。 |
| `hide_native_tools` | `true` | 隐藏主模型可见的 AstrBot 原生工具，默认只保留五个 maid 工具（及 `native_tool_whitelist` 中的白名单工具，改配置即时生效、无需重启）。 |
| `native_tool_whitelist` | `[]` | 仅在 `hide_native_tools=true` 时显示并生效。白名单中的工具（如 `read_channel`、`send_message_to_user` 等）仍直接暴露给主模型，支持自动下拉选择当前已有工具。 |
| `hide_transfer_tools` | `true` | `hide_native_tools=false` 时，额外隐藏主模型可见的全部 `transfer_to_*` 工具，maid 工具仍可用。 |
| `show_maid_speech` | `false` | 是否把管家干活途中的正文（没有正文时用推理）即时发到聊天。终答始终留给大小姐转述，不受此项影响。 |
| `show_maid_tool_status` | `false` | 是否把管家的函数调用状态发到聊天（`管家名: 🔨 调用工具: xxx`），对齐 AstrBot 的「输出函数调用状态」。模型不输出正文时这是唯一的实时进度信号；长任务会一步一条。 |
| `include_raw_user_input` | `true` | 开启时把真实用户原话一并透传给管家；关闭后只传大小姐的任务请求。 |
| `log_raw_llm_io` | `false` | 开启后在 DEBUG 日志打印完整 LLM 原始请求/响应，可能包含敏感信息。 |
| `dispatch_prompt_template` | 内置 | 发送给管家的调度提示模板，只允许 `{user_input_block}`、`{maid_request_block}` 两个占位符（用户原话块 / 大小姐请求块）。管家的「身份」请配置在 SubAgent 的人格里，这里只管派活格式。 |
| `memory_agent_names` | `[]` | 启用持久记忆与原生 Read/Write/Edit 文件的管家名称列表。 |
| `max_workers` | `3` | 所有聊天来源合计同时干活的管家上限，1～16。满了排队；有人发来的新输入可多用 1 个位置；控制台会话不计入。 |
| `inferred_dispatch` | `true` | 自我唤醒时是否允许派发；允许时必须填写评估表单。 |
| `inferred_rules` | `[]` | 自我唤醒派发规则，每条有 `id`、`name`、`enabled`、`instruction`。为空时跳过规则判断，方向与证据照常校验。在控制台设置弹窗里按 JSON 数组编辑，格式错误时不会保存这一项的改动。 |
| `retention_days` | `30` | 会话记录保留天数（不删 memory）。 |
| `session_idle_timeout_hours` | `5` | 全部任务结束后的空闲窗口，正数小时，可填写小数；任意插件工具调用刷新。 |

## SubAgent 配置示例

在 AstrBot 全局配置或管理面板中配置一个 SubAgent（`name` 需在插件 `allowed_agent_names` 白名单内，插件对名称做大小写适配）：

```yaml
subagent_orchestrator:
  agents:
    - name: butler
      enabled: true
      system_prompt: |
        你是运行在 AstrBot 中的管家，一个基于终端的执行助手，
        作为子代理接收主代理的指令并实际执行。

        ## 工作原则
        1. 需要主对话背景时用 maid_read 读取，不重复已经完成的调查。
        2. 做完用 maid_report 上报 ready；需要人回答时带上 human_action。
        3. 主动决策 —— 遇到模糊处优先做合理假设并继续，在结果中说明假设；
           仅在任务完全阻断时才返回失败，不进行无休止追问。
        4. 结果导向 —— 产出明确交付物，不要过程废话。
```

> 不想手动配置？什么都不填即可——插件会自动创建一个名为 `butler` 的默认管家（使用全部工具，人格与调度模板同源）。
